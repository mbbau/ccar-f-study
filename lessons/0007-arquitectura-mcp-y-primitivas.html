1 · El panorama: las tools se mudan a otro programa

Hasta ahora, en los Días 01 y 02, tu programa definía las tools (el JSON con name, description e input_schema) y las ejecutaba. Con MCP (Model Context Protocol), las dos cosas pasan a un programa aparte, el servidor MCP. Así, un mismo servidor sirve para cualquier aplicación que hable el protocolo: Claude Code, Claude Desktop o tu propio agente.

servidor MCP: define y ejecuta⇄host (tu programa / Claude Code)⇄Messages API: Claude decide

Lo que no cambia: el request sigue siendo model + max_tokens + system + tools + messages, y Claude sigue pidiendo con tool_use. Para Claude, una tool MCP es una tool más.

Lo estás usando ahora

Esta sesión de Claude Code tiene conectados servidores MCP (por ejemplo, el de Atlassian). Sus tools me aparecen con nombres como mcp__claude_ai_Atlassian__getJiraIssue: mcp__ + servidor + __ + tool (Claude Code, permisos MCP). Probá /mcp en tu Claude Code para ver los tuyos.

2 · Host, client, server

RolQué esEn el ejemplo
Host“The AI application that coordinates and manages one or multiple MCP clients”Claude Code, o tu agente en Python
ClientVive dentro del host y mantiene la conexión con un servidorUno para el DWH, otro para Jira
Server“A program that provides context to MCP clients”El servidor del DWH de la hormigonera

La relación es 1:1: “The MCP host accomplishes this by creating one MCP client for each MCP server” (MCP architecture). Los mensajes entre client y server son JSON-RPC 2.0: métodos como tools/list o tools/call (spec 2025-11-25).

Versiones de la spec: hasta la 2025-11-25, la conexión empieza con un initialize en el que client y server negocian capabilities. La 2026-07-28 (la más nueva) es stateless: cada request lleva su versión y sus capabilities (spec latest). La guía del examen no entra en ese detalle. Quedate con la idea: antes de usar nada, el client averigua qué ofrece el servidor.

3 · Las tres primitivas: ¿quién decide usarla?

Un servidor puede ofrecer tres cosas. La diferencia no es técnica sino de control: quién elige cuándo se usa (Server concepts).

PrimitivaLa controlaQué esEn Claude Code
ToolEl modeloUna función que Claude invoca en medio del loop: hacer algo o calcular algo con argumentos que él arma. “the language model can discover and invoke tools automatically” (spec: tools).Aparece como tool mcp__servidor__tool
ResourceLa aplicaciónContenido de solo lectura con una URI (un esquema, un archivo, un catálogo). “host applications determining how to incorporate context based on their needs” (spec: resources).Lo mencionás con @servidor:protocolo://ruta y se adjunta
PromptEl usuarioUna plantilla que el usuario elige a propósito, con o sin argumentos, “for example, as slash commands” (spec: prompts)./mcp__servidor__prompt

Claude Code: resources con @ y prompts como comandos, en Use MCP resources y MCP prompts as commands.

Lo que pide la guía (2.4): exponer catálogos de contenido como resources (resúmenes de issues, jerarquías de documentación, esquemas de base de datos) “to reduce exploratory tool calls”. Si el esquema del DWH es un resource, el agente sabe qué tablas hay sin gastar cinco tool calls preguntando.

Trampa del día (issue #4)

Exponer como tool algo que es un resource de solo lectura: listar_tablas(), get_diccionario_kpis(). Funciona, pero obliga al modelo a explorar con llamadas. Ojo con el reverso: “solo lectura” no alcanza para que algo sea resource. Una SELECT con la consulta que arma Claude sigue siendo una tool, porque la elige el modelo con sus argumentos.

4 · Un pedido de punta a punta

El tutorial oficial de cliente MCP lo muestra en Python. El host le pide las tools al servidor, las convierte al formato de la Messages API y, cuando Claude devuelve tool_use, ejecuta la llamada en el servidor (Build an MCP client):

tool_list = await client.list_tools()                     # tools/list
available_tools = [{"name": t.name,
                    "description": t.description,
                    "input_schema": t.input_schema} for t in tool_list.tools]
response = anthropic.messages.create(model=MODEL, max_tokens=1000,
                                     messages=messages, tools=available_tools)
...
elif content.type == "tool_use":
    result = await client.call_tool(tool_name, tool_args)  # tools/call
  1. El client se conecta al servidor y averigua qué ofrece.
  2. tools/list: recibe name, description e inputSchema de cada tool.
  3. El host las pone en el parámetro tools del request. Si no están ahí, Claude no las conoce (Día 05).
  4. Claude responde stop_reason: "tool_use" con un bloque tool_use.
  5. El client llama tools/call en el servidor. Claude nunca habla con el servidor.
  6. El host agrega un mensaje user con el bloque tool_result. MCP marca las fallas con isError; la Messages API, con is_error.

Y del lado del servidor, en Python (SDK oficial, rama v1.x con FastMCP; la 2.x usa MCPServer con los mismos decoradores) (python-sdk):

mcp = FastMCP("Demo")

@mcp.tool()                          # la elige el modelo
def add(a: int, b: int) -> int: ...

@mcp.resource("greeting://{name}")   # contenido con URI
def get_greeting(name: str) -> str: ...

@mcp.prompt()                        # plantilla para el usuario
def greet_user(name: str) -> str: ...

5 · Elegir servidores y describir bien sus tools (2.4)

  • Comunidad antes que propio. Para integraciones estándar (Jira, GitHub), usá un servidor existente. Reservá los servidores propios para los flujos específicos del equipo (guía 2.4). Antes de conectar uno, confirmá que confiás en él: “Servers that fetch external content can expose you to prompt injection risk” (Claude Code MCP).
  • Todas a la vez. Las tools de todos los servidores configurados se descubren al conectarse y quedan disponibles al mismo tiempo (guía 2.4). Para que no llenen el contexto, Claude Code usa tool search: al principio carga solo los nombres y trae la definición cuando la necesita (tool search).
  • Descripciones que compitan con Grep. Si la description de dwh_buscar_columna es pobre, el agente prefiere las tools nativas (Grep) aunque la tuya sea mejor. La description tiene que explicar qué hace, qué devuelve y cuándo usarla (guía 2.4). Es la lección 0002 aplicada a MCP.

Del lado del client también hay primitivas: elicitation (el servidor le pide un dato al usuario), y sampling y roots, que la spec 2026-07-28 marcó como deprecated (Client concepts). Para el examen, alcanza con saber que existen.
