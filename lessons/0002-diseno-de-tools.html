1 · Cómo elige Claude una tool

En cada request le mandás la lista tools. Para decidir si llamar a una y a cuál, Claude solo tiene tres cosas: name, description e input_schema. No ve tu código ni tu base de datos.

La idea central del día

La doc: “Provide extremely detailed descriptions. This is by far the most important factor in tool performance” (docs). La guía del examen lo dice así: las descriptions son el principal mecanismo de selección del modelo (task statement 2.1).

Pensalo como el diccionario de datos de un modelo semántico: si una medida se llama Total y no tiene descripción, cualquiera que llegue nuevo la va a usar mal. Con las tools, ese “alguien nuevo” es Claude en cada llamada.

2 · Anatomía de una buena description

La doc pide al menos 3–4 oraciones que cubran:

  1. Qué hace.
  2. Cuándo usarla, y cuándo no.
  3. Qué significa cada parámetro (va en la description de cada propiedad del input_schema).
  4. Límites o advertencias.
MalaBuena
"Consulta datos." "Ejecuta una consulta SQL de solo lectura (SELECT) sobre la tabla despachos y devuelve las filas como texto. Usala cuando necesites cifras de despachos: m3, precios, plantas o clientes. No la uses para descubrir qué tablas existen. Si no hay coincidencias devuelve 0 filas, lo cual no es un error."

Ejemplo adaptado del patrón bueno/malo de la doc oficial.

3 · Sin superposición: ni tools genéricas ni duplicadas

El objetivo es que para cada pedido haya una sola tool obviamente correcta. Eso falla de dos maneras:

  • Tools que se pisan: buscar_cliente y obtener_cliente con descriptions parecidas. Claude elige al azar. Solución de la guía (2.1): diferenciar las descriptions o renombrar para eliminar la superposición.
  • Una tool genérica que hace de todo: un consultar(algo) ambiguo. La guía propone separarla en tools con propósito específico.

Y al revés, Anthropic advierte contra envolver cada endpoint de una API en una tool: “More tools don't always lead to better outcomes”. Mejor buscar_contactos que listar_contactos devolviendo todo (Anthropic Engineering). Otra práctica útil: prefijos por servicio (dwh_…, jira_…).

4 · Cuántas tools le das y cómo forzar su uso

Según la guía (2.3), demasiadas tools degradan la selección. A cada agente le das solo las que necesita para su rol (principio de especialización). Esto vuelve en el Día 06 con subagentes.

tool_choice controla si Claude puede o debe usar tools:

ValorComportamiento
{"type": "auto"}Default. Claude decide si usa alguna tool.
{"type": "any"}Debe usar alguna tool, sin elegir cuál.
{"type": "tool", "name": "..."}Debe usar esa tool.
{"type": "none"}No puede usar tools.

Detalles de la doc: con any o tool Claude no escribe texto antes del tool_use. Y en los modelos más nuevos (p. ej. Opus 5.5) any y tool devuelven error 400; la alternativa es auto con strict tool use. Para el examen, quedate con la semántica de la tabla: any garantiza que haya una llamada a tool.

5 · Errores estructurados

Ayer viste is_error. Hoy, qué poner adentro. La guía (2.2) distingue:

CategoríaEjemplo en un DWH¿Reintentar lo mismo?
TransitorioTimeout de BigQuerySí, en unos segundos
ValidaciónSQL con una columna que no existeNo: hay que corregir el input
NegocioPedir datos de un mes futuroNo: la regla no cambia
PermisoTabla de costos restringidaNo: sigue sin acceso
{"type": "tool_result", "tool_use_id": "toolu_01", "is_error": true,
 "content": "[permiso] Sin acceso a la tabla 'costos'. Reintentable: no. Informá al usuario que ese dato está restringido."}

Anthropic pide mensajes de error accionables, que le digan al agente qué hacer distinto, en lugar de códigos opacos o tracebacks (fuente).

Trampa típica

Devolver “sin resultados” cuando en realidad falló el acceso, o marcar como error una consulta que devolvió 0 filas. La guía lo pide explícito: distinguir una falla de acceso de un resultado vacío. Si los confundís, Claude le dice al usuario “no hubo ventas” cuando en realidad no pudo mirar.
